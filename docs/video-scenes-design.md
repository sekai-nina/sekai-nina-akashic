# 動画の場面と、スマホで編集する素材（#394）

`/video-scenes` → `/video-scenes/:assetId`。元動画を一度通して見て気になる瞬間を残す入口と、事前に拾った場面から見どころに気づく入口を同じ画面に置く。既存の `/clips` は記事の抜粋プールなので、投稿用の画像・動画とは分ける。

## フロー

- 動画アセット詳細から開く。顔パネルの秒数からも、その時刻の元動画を開ける。
- 場面ごとのカードに、切り抜き・表紙・複数のスクショをまとめる。一覧は幅 640 の非公開サムネイルだけを遅延読み込みし、動画は `preload="none"`。
- 暫定で 3 分以下はスクショだけ。長い動画は小さい顔や他の人へのリアクションも落とさず、本人として検出された区間を候補にする。「かわいい」「笑顔」「発言」を意味として理解した判定は行っていない。
- 区間は前 5 秒・後ろ 3 秒を目安に無音へ寄せる。重なる範囲を結合し、長い区間は無音・画面切替で分け、分割点の前後を重ねる。元の画角と、元に音声があれば音声を残す。
- 「元動画の前後を見る」で文脈を確かめる。元動画を見ながら、そのコマのスクショをブラウザで保存することもできる。
- 保存範囲は開始・終了の秒数、または「開始／終了を今の位置に」で指定。1 本 90 秒以内をワーカーへ書き出し依頼し、長い元動画全体をダウンロードしない。画面には秒数・元動画の容量からの概算と、生成後の実容量を分けて表示する。
- 書き出した範囲は共有の依頼として DB に残る。「保存用に準備した動画」の直近 20 件から、スマホで同じページを開いて保存できる。生成済みの候補をそのまま保存することもできる。

90 秒は X の仕様ではなく、スマホで扱いやすくするためのこの機能の暫定上限。最後の細かい編集・投稿はスマホ側で行う。X への投稿機能は持たない。

## データと認可

生成状況の確認は 10 秒ごとに ID と status だけを読み、変化したときに場面・ファイルの情報を取り直す。タブが非表示なら止め、連続確認は 30 分で終了する。その後は「生成状況を更新」で確認する。

`VideoSceneTask` は `analyze` / `export` の生成依頼、`VideoSceneFile` はその依頼に属する画像・動画。汎用 `Asset` に機密のスナップショットを複製しない。両テーブルとも親動画の **現在の classification** で RLS を効かせる。元動画を上位機密に変えると、依頼・生成物も即座に下位の人には見えなくなる。

読み書きは `withClearance`。依頼・ワーカーの操作は admin / member。viewer は閲覧・見える素材の保存だけ。画面の認証・role は Server Action 内でも検査する。

生成物は `VIDEO_SCENES_DRIVE_FOLDER_ID` の専用フォルダへ置く。アップロード時に anyone / domain 公開のフォルダを拒否し、公開権限を作る `finalizeDriveUpload` や公開 R2 は使わない。Drive の appProperties で、依頼・出力ファイル・処理期限のトークンに結びつける。任意の Drive ファイルを登録できない。

配信は認証済み `/api/video-scenes/media/:id`（元動画は `?source=1`）。4 MB ごとの Range、`private, no-store`。画像は 4 MB 以下、動画は 100 MB 以下。保存時も選んだファイルだけを Range でつなぎ、途中のログインページや異なる範囲は保存しない。

ブラウザの配信はセッションと通常の MFA を維持する。Cookie を持たないワーカーの元動画取得は、API キー認証専用の `/api/v1/video-scenes/assets/:assetId/source` を使う。

## ワーカー

`scripts/video-scene-worker.py` を omokage と同じ Python 環境で動かす。必要なのは InsightFace / numpy / OpenCV と ffmpeg / ffprobe。HTTP・推論・エンコードを Web の応答中に行わない。顔認識の参照は `--refs` に NPZ（`ids`, `matrix`）を渡す。参照の更新は omokage 側と同じ運用で行う。

```sh
# キーは環境から注入する。コマンド引数やログに書かない。
# AKASHIC_BASE_URL=https://<akashic のホスト>
# AKASHIC_VIDEO_WORKER_KEY=<専用 member/internal ユーザーの video_scene_worker キー>
python scripts/video-scene-worker.py --refs /path/to/refs-full.npz --max-jobs 1 --discover
```

既定は待っている依頼を 1 件処理して終了。`--discover` を付けると、依頼が無いときに本人の人物タグ・確定した顔を持つ新しい動画を 1 件だけ依頼して処理する。書き出し依頼を先に処理する。無限ループは作らず、必要なら systemd timer 等で繰り返し呼ぶ。元動画20GB以下、1回の処理は既定2時間まで。分析は既定20分を目安に安全な区間境界で正常終了し、同じ依頼をキューへ戻して続きを処理する。全体を2時間以内に終える必要はない。子プロセスはCPUスレッドを抑え、hard timeoutで終了する。

処理の取得は行ロック + `SKIP LOCKED`。10 分の lease を 45 秒ごとに延長し、期限切れは再取得できる。古いトークンの完了・アップロード・期限延長は拒否する。3 回処理されても期限切れになった依頼は failed にして、人が再試行する。同じ動画の分析、同じ開始・終了（0.1 秒単位）の書き出しは一意キーとトランザクションロックで重複を防ぐ。

作業用の一時ファイルは処理後に削除する。Drive へのアップロード途中でプロセスが失われた場合、未登録の Drive ファイルが残る可能性がある。自動削除は行わず、専用フォルダの appProperties によって対象を下見してから整理する。

### 顔認識との連携（時間的一貫性）

`collect-video-evidence.py` の `Scorer` / `Tracker` を共用する（#452、omokage #9 と同じ負例 margin 0.05、IoU 0.1・特徴量 cosine 0.6・追跡間隔1.1秒・カット差55）。判定名を使わず顔を追跡し、他メンバーとの差も記録する。顔画像や特徴量を外部のAIに送らない。

候補選びは自動タグより広くする。同じ顔の連続2コマ（類似度0.4以上・検出0.5以上・次候補との差0.05以上）、または強い単発（類似度0.5以上・検出0.65以上・同じmargin）を残す。別人・カット・0.51秒より長い空白を支持に使わない。顔のサイズ・笑顔・正面を採用条件にしない。短尺のスクショのみ・長尺の90秒以内という保存方針は変更しない。旧オフラインの `--frames` データは従来の候補規則で評価できるが、新しい解析は必ず追跡情報を持つ。

分析依頼をclaimできたときだけ、ワーカーの`--sync-references`が`video-scenes-references.service`を起動し、`sync-scene-references.py`で公式・正解付きの手本と顔APIの確定・却下を同期する。空の待ち行列では同期しない（systemdの`ExecStartPre`では呼ばない）。同期中も元の依頼のheartbeatは継続する。顔ワーカー用の既存鍵は同期サービスだけに渡す。切り抜き用鍵の権限は増やさない。全ページ取得は最大100ページ・50,000件・4分、サービスは5分・512Mまで。失敗した同期で手本を置換せず、解析も開始しない。NPZは0600・原子的置換、同じ内容なら変更せず、処理開始時に私有作業ディレクトリへコピーして固定する。

解析版は `scene-temporal-v2` に上げ、旧解析の途中保存を混ぜない。区間の最後の追跡状態と画面比較用縮小画像も原子的に保存し、再開前後で追跡を維持する。素材内の各顔の特徴量は保存せず、次区間に必要な末尾の追跡状態だけを保持する。すでにreadyの場面は自動で消したり全件再生成したりしない。新しい依頼・失敗した依頼の再試行から新判定を使う。

集合場面で複数の顔が新奈と推定される場合も、隣接コマの全候補から同じ追跡IDを探す。支持が成立した顔を優先し、構図判定と採用判定で同じ顔を使う。手本同期は1ページずつ復号し、base64レスポンスを全件保持しない。行列の検証も1024行ずつ行い、大きな一時配列を作らない。

2026-11-21、同期処理を512M制限下で検証し、API相当の100ページ・50,000件＋公式等743件の作成・保存・同一内容の再保存が成功（最大RSS 406,872 KiB）。これは合成手本の負荷試験であり認識精度評価ではない。実APIでも確定・公式10,944件／却下6,071件の同期に成功した。

### 長尺の途中保存の詳細

永続キャッシュと元動画の検証可能なSHA-256がある分析依頼は、`--slice-seconds`（既定1200秒）で継続処理する。顔認識は60秒区間の完了後、素材生成は場面の境界、アップロードはファイル境界で区切る。rendererの終了コード75は失敗ではなく継続要求。APIの`yield`で同じ依頼をqueuedへ戻し、次のtimerで再取得する。最大128回までで、クラッシュ・lease失効の3回制限とは別。HTTPの一時エラーは元動画GETを最大3回、継続可能な分析の一時障害は最大3回だけ再試行する。認可エラーを自動再試行しない。

固定した参照は区間間で変更せず、原子的コピーで保存する。継続中の`.continuing`マーカーの最終更新から24時間以内は手本の再同期も省き、同じ手本を使う（継続のたびに更新するため、ジョブ全体の経過時間の上限ではない）。登録済み素材IDはclaimの現在のDB状態とローカルSHA台帳の両方で確認する。アップロード済みの素材を区間ごとに作り直さない。

元動画は処理サーバーからGoogle Driveへ直接取得し、MacもVercelも中継しない。`claim`が現在のRLSを通した元動画の`sourceDriveFileId`・`sourceBytes`を返し、サーバーだけに保管した専用`drive.readonly`認証（`--drive-credentials`、JSONは0600）で取得する。取得は4MBずつ、途中ファイルからRange再開し、末尾の1byte・総容量と全体SHAを再確認する。credential・access tokenはrendererやログへ渡さない。既存の`--source-cache-dir`も再利用できる。直接認証が未設定の場合の旧API取得は残り200MBまでで、大容量をVercelへフォールバックさせない。

初回の認証設定は`setup-scene-drive.py authorize --client-env <サーバー既存OAuth設定> --credentials <私有JSON> --listen`で行う。既存のclient ID/secretだけを利用し、既存refresh tokenはコピーしない。認可scopeは`drive.readonly`だけ、PKCE・stateを検査して15分で終了し、token交換と保存はサーバー上で行う。認可の戻り先は`http://localhost`で、必要なら初回のみSSH転送でサーバーの127.0.0.1:18080へ接続する。これは認可コールバックだけで、動画は転送しない。以後Macの起動は不要。Googleが返した実scopeも設定時・更新時に検査し、更新権限を含むtokenは拒否する。

直接取得の直前にもAkashicのheartbeatでRLSとleaseを確認する。以後45秒ごとのheartbeatが401/403/404/409を返したら1回で失効扱い、一時障害は連続3回で停止する。検知後はGETの前後・再試行ごとにキャンセルを確認して未保存chunkを破棄し、renderer待機も1秒ごとに確認して子プロセス群を回収する。通信中のGETには最大40秒のtimeoutがあり、検知と同時にネットワークソケットが切れる保証ではない。

継続時も元動画の全体SHAを再照合するため、動画サイズに比例したローカルディスクI/Oは発生する。Vercelへの動画再転送ではない。キャッシュの取り違え・破損を検出する安全策として維持し、長尺実地検証では推論時間と分けて負荷を見る。

分析サービスは `--cache-dir ~/.cache/akashic-video-scenes` を使う。ディレクトリは0700。元動画はRange取得を途中から再開し、顔認識は60秒区間を順にデコードして区間完了ごとにJSONを原子的に保存する。間引き間隔（短尺4fps／長尺2fps）、モデル、認識閾値、画角は変更しない。1 CPUのquotaに合わせ、ONNX Runtime・OpenCV・BLASのスレッドも抑える。

再試行時は完成した区間・構図判定・無音判定・画像／動画を再利用する。タスクと元動画の `sourceRevision` を外側の識別子にし、実ファイル・参照NPZ・アルゴリズム版のSHA-256を内側の識別子にする。Drive上の元ファイルのSHA-256をclaim時に取得し、ダウンロード後にも照合する。取得できない場合は永続キャッシュを使わない。生成ファイルもSHA-256で確かめる。キーの変更・参照の更新で古い結果を混ぜない。認可は再取得・heartbeat・完了時にも現在のRLSで検査する。

成功した依頼のローカル作業キャッシュは削除し、失敗・正常な継続終了では保持する。自分のマーカーがある非稼働キャッシュだけを整理し、他に残すのは直近2件・7日以内まで。空き容量は保存済み元動画・生成物を差し引いた残作業分と2GBの余裕を確認し、容量不明なら最大値で予約、取得時の実容量でも再確認する。生成素材合計は1件10GBまで。元動画・Driveの素材は削除しない。1回のhard timeoutと既存CPU・メモリ上限は維持する。タイムアウト時は子孫のffmpegも終了させる。ログは区間・工程の進捗とHTTPステータス番号までで、鍵やURLを記録しない。

構図情報はuint8配列として生成・NPZ保存し、JSONの全コマのリストとfloat64配列を同時に持たない。比較する2コマだけをその場で正規化する。原子的な保存とファイルハッシュの検証に加え、未マークの既存ディレクトリを採用しない。rendererが先に終了した場合でも、プロセスグループを別に確認して残存ffmpegを回収する。

2026-11-21、以前2時間で失敗した799,142,531 bytes・約25分の実動画を同じCPU 100%／メモリ1800Mで検証。約92分で39場面・47スクショ・39動画を生成し、メモリpeakは1.6Gだった。完成キャッシュのハッシュ検証と再利用は約8秒で成功。区間処理を途中で中断して保存済み区間から復帰する経路は回帰テストで確認した（実動画の初回処理は中断前に完了）。24時間の最大入力での実測ではない。

元動画を見ながらの範囲指定は、場面候補の分析前でも依頼できる。未分析ならワーカーの ffprobe で実際の長さを確かめ、動画外の範囲は出力しない。`--export-only` は保存用の書き出しだけを処理する。分析中に保存を待たせない運用では、分析用 timer と書き出し専用 timer を分ける。`--export-only` と `--discover` は併用不可。1依頼の出力はサムネイル込み4,000ファイル・2,000場面まで。件数超過は素材生成・アップロード前に検査する。

`deploy/video-scenes-*.service` / `.timer` は sekai のユーザーユニット。コードは `~/akashic-video-scenes/scripts`、参照は `data/refs-full.npz`、鍵は `~/.config/akashic-video-scenes/worker.env`（0600）へ配置する。Python は既存の `~/sekai-nina-omokage/.venv` を使う。分析は完了後10分、書き出しは完了後1分ごとに1件。分析 CPU 100% / 1800 MB、書き出し CPU 50% / 512 MB に制限し、既存サービスは変更しない。timer は1件の実地確認後に有効化する。

## 一覧の絞り込み（種類・長さ）

`/video-scenes` の一覧は `?kind=` / `?length=` / `?sort=` で絞り込み・並べ替えができる。条件は `src/lib/video-scenes/filters.ts`。

- 種類: 番組・配信 / トーク / TikTok / ゲーム / その他。取り込み元の `SourceRecord.publisher`（`Talk (Sony Music)` / `TikTok` / `ひなこい`・`UNI'S ON AIR` / `Lemino`・`日向坂ちゃんねる`）と番組タグで決め、1 本は 1 種類にだけ入る。Instagram の動画は出典もタグも無いので「その他」
- 長さ: 〜1分 / 1〜10分 / 10分以上。`Asset.durationSec` を使い、長さ不明（null）はどれにも入らない（「すべて」には出る）
- 並び: 新しい順（既定）/ 長い順（長さ不明は最後）

`Asset.durationSec` は `GET /api/cron/video-durations`（`9,24,39,54 * * * *`）が、長さが空の gdrive の動画を 400 本ずつ Google Drive の `videoMediaMetadata.durationMillis` から埋める。ダウンロードせず、取り込み側（bot）も触らない。Drive が長さを持っていないもの（処理待ち・作れない形式、ファイルが無い）は 1 日おきに 3 回まで問い合わせ直し、それでも無ければ「長さ不明」のまま。一時的な失敗（5xx / 429）は回数に数えない。件数は `/status` の `cron.video_duration` のメッセージ（「長さ不明 N」）に出る。既存の動画は `pnpm cli:fill-video-durations --apply` で一度に埋める（既定は 50 本だけ問い合わせる下見）。多くが「長さ不明」に残るなら、sekai の場面ワーカーと同じ環境で ffprobe して埋める経路を足す。

## 適用順と検証

1. migration `20261116000000_video_scene_tasks` と両テーブルへの GRANT を、承認後に適用する。
2. 認証アカウントだけが読める専用 Drive フォルダを用意し、Web 側に `VIDEO_SCENES_DRIVE_FOLDER_ID` を設定する。
3. Web を反映し、ワーカーに専用 API キー・API URL・参照ファイルを設定する。最初は `--max-jobs 1` で 1 件確かめる。
4. 元動画から範囲を選ぶ → 書き出し → スマホで保存、と、候補から元動画の前後を見る動線を実機で確かめる。その後に timer を有効にする。

2026-11-18 に本番反映済み（#449）。migration と両テーブルの `app_runtime` GRANT、専用非公開 Drive フォルダ、専用 member/internal ユーザーの `video_scene_worker` キー、Web、sekai の分析・書き出し timer を適用した。既存の omokage-worker は変更していない。

- ローカル PostgreSQL: `node scripts/check-video-scenes-rls.mjs`。.env を読まず、ネットワークを持たない一時コンテナを作って終了時に破棄する。8 ポリシー、下位・未設定 clearance、書き込み拒否、親の再分類、保存範囲の制約を検証する。

- オフラインの生成検証: `video-scene-worker.py render --source <動画> --out <一時フォルダ> --kind analyze --frames <保存済みの frames.json>`。`--kind export --start 5 --end 12` は指定範囲だけの動画を作る。
