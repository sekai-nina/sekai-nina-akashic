# 顔認識 設計書

画像に写っている日向坂46 のメンバー（卒業生を含む）を推定し、アセットの人物タグ（`AssetEntity`）として付ける。

- 段階 1（#376）: 精度実験。[sekai-nina-omokage](https://github.com/sekai-nina/sekai-nina-omokage) で正解付けと評価
- **段階 2（#384）: 結果を置く DB とワーカー用 API（この文書の中心）**
- 段階 3: 推論ワーカー（omokage。`sakura` か `sekai` に常駐）
- 段階 4: 確認 UI と人物での検索

## 方式

InsightFace の付属モデル（buffalo_l。Fine-tuning しない。非商用なら無料のライセンス）で顔を検出し、顔ごとに特徴量（512 次元）を作る。参照（アー写と、人が確定した顔）とのコサイン類似度がいちばん高いメンバーを候補にし、類似度が閾値以上ならそのメンバーと判定する。

推論はワーカーの手元の CPU で完結し、画像を外部のサービスに送らない（文字起こし・OCR との違い）。

### 段階 1 の結果（#376）

732 顔に人の目で正解を付けて評価した。閾値 0.40 のとき:

| 参照 | 現役 P / R | 卒業生 P / R | 坂井新奈 P / R |
|---|---|---|---|
| アー写だけ | 99% / 89% | — / 0% | 100% / 94% |
| アー写＋正解付きの顔 | 98% / 93% | 99% / 98% | 100% / 100% |

- 既存の person タグはほとんどが「ブログの書き手」（`author`）で、写っている人ではない。評価の正解には使えなかった
- 人が確定した顔を参照に足すと recall が上がる（卒業生はアー写が 0 枚でも 98%）。これが下の「確定した顔を参照に返す」の根拠

## データ

### `FaceDetection`（検出した顔 1 つ）

| 列 | 内容 |
|---|---|
| `x1` `y1` `x2` `y2` | 顔の枠。画像の幅・高さに対する 0〜1 の割合（サムネイルでも元画像でも同じ値で描ける） |
| `detScore` | 顔検出の確からしさ |
| `embedding` | L2 正規化した float32 × 512 のリトルエンディアン（2,048 バイト）。`Bytes` で持つ |
| `predictedEntityId` / `similarity` | いちばん似ていたメンバーと類似度 |
| `status` | `auto`（自動で付けた）/ `pending`（人の確認待ち）/ `confirmed`（人が確定）/ `rejected`（人が却下） |
| `confirmedEntityId` | 人が付けた正解。`confirmed` で null ならメンバー以外の人。`rejected` でも正解が分かれば入れる |
| `modelVersion` | 推論したモデル（例: `buffalo_l@1`） |

### `FaceScan`（どの画像をどのモデルで処理したか）

`(assetId, modelVersion)` で 1 行。顔が 0 個の画像を何度も処理しないために持つ。モデルを変えたら `modelVersion` を上げれば、全画像が queue に戻る。

取り直しても直らない失敗（元画像が Drive に無い・大きすぎてサムネイルも無い・画像として読めない）も、`error` に理由を入れて行を作る。作らないと、その画像が新しい順の queue の先頭に居座り、失敗が `limit` 件たまると他の画像が処理されなくなる。やり直すときは行を消す。一時的な失敗（Drive の 5xx など）では行を作らず、次の回に取り直す。

### 機密レベル

どちらも保護テーブル。自前の `classification` は持たず、`AssetEntity` と同じく親 Asset の `classification` で 4 操作の RLS を張る（`20261110000000_face_detection`）。

ワーカー用のユーザーは `internal` にする。2026-11-09 時点で本番の画像 71,600 枚はすべて `internal` で、`confidential` 以上の画像は 0 枚。推論は外部に送らないので機密の画像も扱えるが、入ってきたらそのとき決め直す。

### 特徴量を DB に持つ理由

人が確定した顔を参照に足すには、どこかに特徴量を置く必要がある。ワーカーに持たせると、サーバーを移すときや壊れたときに全画像を推論し直すことになる。約 10 万顔で約 200 MB の見込み。

pgvector は使わない。今は「似た顔を DB で検索する」場面が無く、参照はワーカーがまとめて取ってメモリで比べれば足りる。必要になったら `Bytes` から移す。

## 自動で付ける規則

判定は `src/lib/faces/policy.ts` の `decideFace`（純粋関数・テストあり）、書き込みは `src/lib/domain/faces.ts` の `writeFaceResults`。

1. 類似度が **0.40 以上**なら `auto` にして、`AssetEntity`（`roleLabel = "face"`）を付ける。閾値はサーバーが持つ（ワーカーは類似度をそのまま送る。閾値を変えるのにワーカーを配り直さなくてよい）
2. 次の場合は閾値以上でも付けずに `pending` にする。**人の判断を機械が上書きしない**
   - 「坂井新奈は出ていない」（`Asset.ninaAbsent`。#261）の画像で坂井新奈と判定した顔。付けると `ninaAppearanceOf` が「出ている」に変わり、人の ❌ が消えてしまう
   - 同じアセットで、人が「このメンバーではない」と却下済み（`rejected`）のメンバー
3. 同じアセットに同じメンバーのタグが既にあれば、`roleLabel` は変えない（`author` を `face` で潰さない）
4. 推論し直すときは、人が見ていない行（`auto` / `pending`）だけを置き換え、`confirmed` / `rejected` は残す
5. 外す `face` タグは、**前回の推論で自動で付けた（`auto` だった）メンバーのうち、今回付かなくなったもの**に限る。`roleLabel` は画面や API から手入力もできるので、「`face`」という文字だけで外すと、人が付けたタグを消してしまう。人が確定した顔のメンバーのタグにも触らない
6. 人が坂井新奈を「出ていない」「未確認」にしたら（`setNinaAppearance`）、坂井新奈として自動で付けた顔を `pending` に戻す。タグは既存の処理で外れるので、`auto` のまま残すと「自動で付けた = タグがある」が崩れる

`mentionsNina`（本文の機械判定）には触らない。坂井新奈の `face` タグが付けば、`ninaAppearance` は既存の定義どおり「出ている」になる。

### 割り切ったこと

- **モデルは 1 つずつ動かす。** 新旧のワーカーが同じ画像に書くと、後から書いた方の結果が残る（人が見ていない行は `modelVersion` を問わず置き換えるため）。モデルを入れ替えるときは、古いワーカーを止めてから新しいワーカーを動かす
- モデルを変えると、人が確定・却下した顔（旧モデルの行）と同じ顔が、新しい行として確認待ちにもう一度出る。タグは壊れない。扱いは段階 4 で決める（#386）

- 人がアセット詳細で `face` のタグを手で外しても、その顔は `rejected` にならない。同じモデルでは推論し直さないので戻らないが、`modelVersion` を上げると付き直す。段階 4 の確認 UI で却下すれば `rejected` が残る
- `face` タグの付け外しでは Drive のバックアップ（`backupAssetToDrive`）を回さない。初回は 7 万枚に付くので、1 枚ごとにバックアップを上げ直すと Drive の API を使い切る。`face` タグは `FaceDetection` から作り直せる
- キャッシュは一覧だけを捨てる（`invalidateAssetList`）。ダッシュボードの統計（`stats`）まで捨てると、初回の約 7 万回の書き込みのたびに、次に開いた人が重い集計を待つことになる。統計は 60 秒で勝手に更新される
- queue の残り件数は画像全体を数えるので、`count=1` を付けたときだけ返す

## API

`/api/v1/faces/*`。**`face_worker` だけを持つキー**で叩く（read / write は持たせない。キーが漏れても他の API は叩けない）。仕様は [api.md の「顔認識」](./api.md#顔認識-faces)。

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/faces/queue` | まだこのモデルで処理していない画像（処理済み・失敗として記録済みは出ない） |
| GET | `/faces/assets/:id/original` | 元画像。`/api/drive-image` はログインのセッションが要るので別に持つ。4.4 MB 超は 413（Vercel の応答上限）で、ワーカーはサムネイルに落とす |
| PUT | `/faces/assets/:id` | 1 枚の推論結果を書き込む |
| GET | `/faces/references` | 参照に足す顔。**人が確定した顔だけ**（自動で付けた顔を返すと、間違いが参照に混ざって広がる） |

ハートビート（`POST /api/v1/jobs/:key/runs`）も `face_worker` のキーで送れる。ただしジョブ名が `omokage.` で始まるものだけ（#389。他の bot のジョブを偽れないように）。

## 読み出し（MCP。#396）

ふぃたんなどの AI からは MCP で読む。`akashic_get_asset` の `faces`（写っている人物・確認待ちの顔の数。ブログ本文などは子の画像の分もまとめる）と、`akashic_search` の `appearing`（顔で写っている人物での絞り込みと、結果の人物）。人物タグの `roleLabel` は書き手の `author` が先に付いていると `face` にならないので、写っているかは `FaceDetection` から返す。詳細は [mcp.md の「写っている人物」](./mcp.md)。

## トークの動画（#403）

タグ「トーク」の動画（200 MB まで）も queue に出す。番組・配信などの長い動画は対象にしない（#394）。

- ワーカーは元ファイルを `Range` で 4.4 MB ずつ取ってつなぐ（Vercel の応答上限のため。sekai に Drive の鍵を置かずに済む）
- 等間隔にコマを切り出して顔を判定し、**メンバーごとにいちばん似ていた顔**を 1 つずつ書き込む（同じ人の顔がコマの数だけ確認待ちに並ばないように）。`frameSec` に何秒目かを入れる。#394 のスクショ・切り抜きでも使う
- 1 コマでも閾値以上なら、画像と同じ規則で `face` タグが付く。Discord への転送も画像と同じ経路に乗る

## Discord への転送（#395）

他のメンバーのトーク・ブログに坂井新奈が写っていたら、discord bot（sekai-nina-discord-bot の `face_forward`）が世界新奈の talk / blog チャンネルに流す。bot は `GET /faces/appearances` を数分おきに叩き、流した画像を自分で覚える。坂井新奈が書き手の画像は API が除く。画像は `GET /faces/assets/:id/original`（`read` のキーで取れる）。

## 本番への適用

migration `20261110000000_face_detection` は本番未適用。適用後に手動 GRANT が要る:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON "FaceDetection" TO app_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON "FaceScan" TO app_runtime;
```

ワーカー用のキーは `internal` の専用ユーザーに発行する（`pnpm cli:keygen <email> omokage-worker face_worker`）。段階 1 で作った `omokage@akashic.local`（`read` のキー）を使い回してよい。
