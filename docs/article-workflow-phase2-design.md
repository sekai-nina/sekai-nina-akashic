# 記事化の流れの一本化・段階2の設計 (#233)

2026-10-17 作成。ユーザーと下記の方針を合意し、`feature/article-workflow-unification` で実装する。

関連: [段階1の合意と設計](./clip-progress-design.md)、Issue #233。

## 目的

素材 → クリップ → ドシエ → テンプレート → 記事 → push の導線を揃える。
ミーグリ・ライブの記事生成も `/dossiers/[id]/article` に寄せる。
観点のチェックをやめる `/coverage` の変更は段階3で扱う。

## 現状の調査

| 入口 | 現状 | 分断している点 |
|---|---|---|
| `/clips` | 選んだ抜粋を新規・既存ドシエへ移せる。完了時はドシエ詳細へのリンクが出る | 次の操作はドシエの種類によって変わる |
| 一般ドシエ詳細 | 「記事にする」「記事に追記する」から `/dossiers/[id]/article` | ミーグリ・ライブ用はボタンの対象外 |
| 一般ドシエの記事画面 | テンプレート選択 → 差分 → 保存。複数記事なら追記先を選べる | ミーグリ・ライブ用は元の進行画面を開くよう案内する |
| ミーグリ詳細 | 素材 → レポ → スケッチ → 記事の4ステップ | この画面に記事のプレビュー・保存が埋め込まれている |
| ライブ詳細 | 公演 → 素材 → レポ → スケッチ → 記事の5ステップ | この画面に記事のプレビュー・保存が埋め込まれている |
| 保存後 | 保存完了メッセージと `router.refresh()`。生成画面の上部から記事を開ける | 本文の確認と公開への次の操作が分散している |

生成のドメイン処理はすでに共通化されている。`article-generate.ts` の `ArticleTarget` は `dossier` / `meetgreet` / `live` を扱い、`ArticleStep` も共通。
画面の入口から適切な target へ接続することで、本文の生成ロジック・既存記事の紐づけを再実装せずに揃えられる。

## 既存の方針として維持すること

- 素材のクリップ済と記事化済を別の印として扱う。
- 本文の生成・追記・出典番号・除外・プレビューと保存の整合検査は共通処理を使う。
- ミーグリとライブのテンプレートは種類で固定する。一般のドシエは現在の選択肢を使う。
- 複数記事への追記先の選択、テンプレート変更の制約、クリップのプールから直接記事を作れない制約を維持する。
- ドシエとミーグリ／ライブの閲覧・編集権限を再確認する。上位機密の器が見えなくても、一般ドシエ扱いへ切り替えて生成してはいけない。
- 保存と公開を分け、公開は現行の admin 向け push で行う。新しい自動公開は追加しない。
- 既存 REST / MCP の入口や生成内容は互換を保つ。

## 段階2の合意事項

**合意:** 記事のプレビュー・保存をドシエ画面に統一し、開催日・公演・レポ・スケッチの編集は今のミーグリ／ライブ画面に残す。

記事化の入口を揃えながら、既存の準備操作と構造化データの編集を保てる。
開催情報・レポ・スケッチの編集は既存画面に残す。

ユーザーの「はい」の回答で合意済み。以下の導線を実装する。

## 共通画面の構成

[操作できるHTML画面案](./mockups/article-workflow-phase2.html) で一般ドシエ・ミーグリ・ライブを切り替えられる。
架空データだけを使い、外部サービスへの通信や実データの保存を行わない。Chrome の隔離した headless プロファイルで3種類の切り替え・プレビュー・保存後表示を確認し、スクリーンショットで表示も確認済み。これは画面案の確認であり、本番アプリの画面確認とは別。

- ドシエの種類によらず、詳細から同じ記事画面へ進む。
- 一般ドシエはテンプレート選択、ミーグリ・ライブは固定テンプレートの表示。
- ミーグリ・ライブは関連する準備画面へのリンクと準備状況を示す。
- 記事画面で差分・除外・保存を扱う。保存後の「記事を開いて編集」「公開の確認へ」を分かりやすくする。公開確認へのリンクは現行権限に従う。
- 元のミーグリ・ライブ画面には記事の状態と共通記事画面へのリンクを残す。
- クリップ移動後は、ドシエの素材確認と記事化へ続けられる導線を用意する。

## 実装箇所の当たり

1. `dossier-article.ts` 周辺に、ドシエから閲覧可能な器・追記先を解決する処理を置く。
2. `/dossiers/[id]/article` と Server Actions を3種類の target に対応させる。見えない器・不整合な template は拒否する。
3. ドシエ詳細、ミーグリ詳細、ライブ詳細、クリップの移動完了表示の導線を接続する。
4. 保存時はドシエ・記事・ミーグリ／ライブの関連ページを無効化する。既存の本文編集と公開操作へのリンクを整える。
5. target の解決・権限拒否・既存記事の選択・旧 API の互換をテストし、`pnpm typecheck` と `pnpm test` を通す。

新テーブルやデータ移行は不要。画面と既存の生成処理への接続を変更する。

## 実装結果

- `/dossiers/[id]/article` を一般・ミーグリ・ライブの共通画面にした。準備情報・固定テンプレート・差分・保存・本文編集・公開確認の順で進める。
- `dossier-article-workflow.ts` でサーバーが生成先を解決する。器の種類・テンプレート・素材ドシエ・既存記事の対応を確認し、見えない器を一般ドシエへ読み替えない。操作ごとに再読込し、member/admin の役割とドシエの編集権限を確かめる。
- 一般ドシエの複数記事選択とテンプレート固定の制約は維持。ミーグリ・ライブは各器の `articleId` を追記先とし、別の記事への指定は拒否する。
- 開催情報・公演・レポ・スケッチの編集は既存画面に残し、記事の生成操作を共通画面へのリンクに置き換えた。既存 Server Action / REST / MCP の経路は削除せず互換を維持する。
- クリップをドシエへ移したあと、「ドシエを開く」と「記事にする」の両方を選べる。
- 保存・除外の復元時は、ドシエ・共通記事画面・該当記事・準備画面・関連一覧を無効化する。
- 保存後は記事の編集へ進め、admin だけに既存の公開確認画面へのリンクを表示する。保存による自動 push は行わない。
- 新テーブル・schema 変更・migration・データ移行は不要。本番データへの書き込み・生成・公開は実施していない。
- 本番の internal 共有範囲で、一般ドシエとライブの生成先を読み取り確認した。ミーグリは対象の共有サンプルが無く、単体テストで確認している。
- ミーグリ・ライブの共通画面でも下書き状態を表示できるよう、既存の記事取得に `draft` を含めた。REST / MCP の記事射影は変更しない。
- 検証: `pnpm typecheck` 成功、`pnpm test` は731成功・8スキップ（54ファイル成功・2ファイルスキップ）。生成先の解決・権限・機密・不整合の拒否、3種類のServer Actionの接続、キャッシュ無効化、共通画面の編集／公開リンクを確認した。
